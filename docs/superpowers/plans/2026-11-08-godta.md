# goDTA : plan d'implémentation

Plan d'implémentation, 8 novembre 2026. Il part de la spec
`docs/superpowers/specs/2026-11-08-godta-design.md` (commit `601e90e`), approuvée par Rudi le même
jour après le panel et le spike (§14 et §15 de la spec). Ce plan ne redit pas la spec : il fixe
les fichiers, les noms, les signatures et les tests, et renvoie à la spec pour le pourquoi.
L'exécutant lit les deux.

Révisé le même jour après la relecture du panel (cinq lecteurs) ; ce qui a été retenu, rejeté,
et vérifié par le contrôleur est dans `2026-11-08-godta-ledger.md`, à côté de ce plan.

> Pour un exécutant agent : skill `subagent-implementation` (ou
> `superpowers:subagent-driven-development`), une tâche par sous-agent. Les étapes sont des cases
> à cocher.
>
> Convention de langue : le code, les messages, les clés JSON, l'aide en ligne et les rapports
> produits par goDTA sont en anglais (le client d'origine est australien) ; ce plan est en
> français, comme la spec.

But : un binaire `godta`, déterministe, qui lit la charge d'une ou plusieurs bases, propose des
index rowstore non cluster sans doublon de l'existant, les mesure par index hypothétiques sur le
serveur ou sur un clone restauré au labo, et écrit pour chaque base un rapport et un script.

Architecture : un paquet par responsabilité sous `tools/internal/godta/`, un binaire
`tools/cmd/godta`. Les parties pures (lecture de plans, rejeu, candidats, couverture, score,
rapport, plan d'exécution) n'ouvrent aucune connexion et se testent hors ligne ; les parties qui
parlent au moteur (collecte, évaluation, clone, labo, nettoyage) ont des tests d'intégration sur
le labo podman. Chaque phase lit et écrit des fichiers JSON dans l'espace de travail (§8.1).

Pile : Go 1.27, `database/sql`, `github.com/microsoft/go-mssqldb` v1.11.0 (déjà dans
`tools/go.mod`), `encoding/xml`, `tools/internal/sqlq`, `tools/internal/sqlplan`. Aucune
dépendance nouvelle.

Découpage : partie 1, tâches 1 à 15, goDTA complet en mode serveur, utilisable seul. Partie 2,
tâches 16 à 19, le mode labo. Une revue de branche à la fin de chaque partie.

## Contraintes globales

Chaque tâche les inclut implicitement.

- Versions prises en charge : SQL Server 2016 SP3 et suivants (spec §4, §15) ; refus explicite
  en dessous (`ProductMajorVersion < 13`, ou 13 sans SP3, `ProductLevel` différent de `SP3`),
  et refus d'Azure SQL Database (`EngineEdition = 5`) et de Managed Instance (`EngineEdition = 8`,
  non mesurée).
- Préfixe de tout objet créé : `godta_<runID>_`, `runID` = 8 caractères `[a-z0-9]` tirés au hasard
  par `crypto/rand` (spec §7.2). Le motif de recherche de `cleanup` est la forme exacte d'un
  identifiant d'exécution, `tsql.RunPattern()` =
  `godta[_][a-z0-9][a-z0-9][a-z0-9][a-z0-9][a-z0-9][a-z0-9][a-z0-9][a-z0-9][_]%` : `godta[_]%`
  seul attrape aussi les objets du jeu de test (`godta_t`, `godta_filt`) et ceux d'un client qui
  aurait choisi ce nom (relecture du plan, mesuré).
- Contexte de base : toute connexion qui travaille dans une base l'ouvre avec cette base dans le
  DSN (`conn.Open(…, database)`), jamais par un `USE` envoyé sur le pool ; le serveur remet ce
  contexte à chaque réutilisation de la connexion. `ALTER DATABASE SCOPED CONFIGURATION`,
  `DB_ID()`, `OBJECT_ID` à deux parties et la session `AUTOPILOT` dépendent du contexte de base ;
  `CREATE INDEX`, `DROP INDEX` et `DBCC SHOW_STATISTICS` acceptent des noms en trois parties
  (mesuré), mais les gabarits restent à deux parties, pour une seule règle.
- Nom d'application de la connexion : `db-ai-toolkit/godta` (spec §6).
- Toute instruction d'écriture vient d'un gabarit de `tools/internal/godta/tsql` ; un nom n'y
  entre que par `tsql.QuoteName`, une chaîne que par `tsql.QuoteString` (spec §7.2).
- Toute séquence qui dépend d'un état de session tourne sur un `*sql.Conn` épinglé ; chaque
  instruction dans son propre lot ; `SET AUTOPILOT ON` seul dans son lot, et son échec arrête
  l'exécution (spec §6, §8.5).
- Une phase d'écriture exige à la fois un profil `readwrite` et `--allow-write`, et n'exécute que
  le plan d'exécution passé par `--plan` (spec §7, §7.1).
- Sortie standard : un seul objet JSON par commande, succès comme échec. Codes de sortie :
  `0` succès, `1` usage, `2` échec après connexion, `3` écriture refusée, `4` connexion
  impossible (spec §10).
- Les secrets ne passent que par `sqlq.Resolver` ; jamais de mot de passe dans un fichier de
  l'espace de travail, un journal ou une sortie.
- Tests d'intégration : sans balise de build, pilotés par `GODTA_TEST_PROFILES` (fichier de
  profils) et `GODTA_TEST_PROFILE` (profil `readwrite`, `"environment": "lab"`), sautés
  proprement quand ils manquent, sur le modèle de `testProfile` dans
  `tools/cmd/sqlq/integration_test.go`. Pour la partie 2, en plus `GODTA_TEST_LAB_PROFILE` (un
  autre conteneur, même version). Chaque test crée sa base `godta_it_<runID>` et la supprime
  dans `t.Cleanup`, même en échec. Jamais `PachaDataFormation`.
- Les tests d'intégration ne comptent que s'ils ont tourné. Le contrôleur donne dans le brief
  les valeurs réelles de `GODTA_TEST_PROFILES` et `GODTA_TEST_PROFILE` (ce plan écrit `…`) ;
  chaque commande de vérification les exporte dans la même invocation du shell que `go test -v`,
  et la porte est la liste des noms attendus, chacun avec sa ligne `--- PASS` ; une ligne
  `--- SKIP` fait échouer la porte, sauf pour un test que la tâche dit facultatif, avec sa
  raison. Go compte un test sauté comme lancé : le nombre de tests seul ne prouve rien.
  `./scripts/build-tools.sh` lance `go test ./...` sans ces variables, donc sans intégration :
  il ne remplace jamais cette porte.
- Commits : messages en anglais, corps en prose qui dit pourquoi, aucun trailer d'attribution.

## Points à surveiller

Ce que la spec implique sans qu'une tâche l'exerce d'elle-même, du plus probable au moins
probable. Chaque ligne a son test, dans la tâche qui possède le code.

1. Noms d'objets qui contiennent `]`, une apostrophe, un espace ou des caractères non ASCII
   (`[dbo].[Order]]s]`, `N'Café'`) : les gabarits doivent produire du T-SQL valide et n'agir que
   sur l'objet nommé. Test dans la tâche 2 (unitaire) et la tâche 10 (une table `[Ord]]er s]`
   dans la base de test).
2. Instance ou base à classement sensible à la casse : les comparaisons de colonnes du modèle de
   couverture se font par `column_id`, jamais par nom, et les requêtes de catalogue ne supposent
   pas la casse. Test dans la tâche 8 (deux colonnes `a` et `A`) et la tâche 5 (base en
   `Latin1_General_CS_AS`).
3. Base dont le Query Store est en `READ_ONLY`, éteint, ou vide sur la fenêtre ; base hors
   ligne, en lecture seule, secondaire non lisible : écartée ou repli, avec la raison, sans
   faire échouer les autres bases. Test dans la tâche 5.
4. Connexion coupée au milieu d'`evaluate`, index hypothétique laissé derrière : le journal le
   retrouve, `cleanup` le supprime. Test dans la tâche 13 (la session de test est tuée par
   `KILL` depuis une seconde connexion).
5. Compilation très longue ou plan énorme : chaque compilation sous délai (`--compile-timeout`,
   défaut 60 s), plan XML lu en flux sans limite de profondeur arbitraire ; une requête qui
   dépasse est marquée `not evaluated (timeout)`. Test dans la tâche 10.

Fichiers :
- Créer : `tools/internal/dotenv/dotenv.go`, `tools/internal/dotenv/dotenv_test.go`

Interfaces :
- Consomme : `sqlq.LoadProfiles`, `sqlq.Profiles.Get`, `sqlq.DefaultProfilePath`,
  `sqlq.NewResolver`, `(*sqlq.Resolver).Resolve`, `sqlq.Profile.DSN`, `sqlq.Profile.ReadOnly`,
  `sqlq.Profile.Environment`.
- Produit :
  - `dotenv.Load(path string) error` et le reste de l'API de sylloge, inchangés (signature lue
    dans `sylloge/internal/dotenv/dotenv.go`) : absent = `nil` ; une clé déjà dans
    l'environnement n'est pas écrasée.
  - `conn.ProfileFromEnv(getenv func(string) string) (sqlq.Profile, bool, error)` : lit
    `GODTA_SERVER`, `GODTA_DATABASE`, `GODTA_AUTH`, `GODTA_USER`, `GODTA_ENVIRONMENT`,
    `GODTA_MODE`, `GODTA_TRUST_SERVER_CERTIFICATE` ; `PasswordEnv` vaut toujours
    `"GODTA_PASSWORD"` pour `auth=sql` ; `false` quand `GODTA_SERVER` est vide.
  - `conn.Select(profilesPath, name string, getenv func(string) string) (sqlq.Profile, error)` :
    profil nommé s'il y a un nom, sinon `ProfileFromEnv`, sinon erreur d'usage.
  - `conn.Open(ctx context.Context, p sqlq.Profile, resolve sqlq.SecretResolver, database string) (*sql.DB, error)` :
    construit le DSN par `p.DSN`, remplace le paramètre `app name` par `conn.AppName`
    (`"db-ai-toolkit/godta"`) et, si `database` n'est pas vide, le paramètre `database`, en
    réécrivant l'URL (`url.Parse`, `Query().Set`), ouvre, `PingContext`. Toute erreur rendue
    passe par `conn.Redact`.
  - `conn.Redact(err error, secret string) error` : remplace le secret résolu, et ses formes
    encodées en URL, par `***` dans le texte de l'erreur (même règle que `redact` de
    `tools/cmd/sqlq/main.go`, copiée : elle n'est pas dans le paquet `sqlq`). `main` y passe
    toute erreur avant de l'écrire en JSON.
  - `type conn.Instance struct { ServerName, MachineName, Edition string; EngineEdition, Major int; Level, Version string; IsEnterpriseFeatures, CanCompress bool; CPUCount int; MaxDOP int; DefaultBackupPath string }`
  - `conn.Identify(ctx context.Context, q Querier) (Instance, error)` et
    `conn.CheckSupported(i Instance) error` (règle des contraintes globales) ;
    `IsEnterpriseFeatures` vrai pour `EngineEdition = 3` (Enterprise, Developer, Evaluation) ;
    `CanCompress` vrai pour `EngineEdition` 3, et pour 2 sauf si `Edition` commence par
    `Web` (Web a `EngineEdition` 2 mais pas la compression ; Standard sait compresser une sauvegarde,
    Express non, mesuré pour Express).
  - `type conn.Querier interface { QueryContext(context.Context, string, ...any) (*sql.Rows, error); QueryRowContext(context.Context, string, ...any) *sql.Row; ExecContext(context.Context, string, ...any) (sql.Result, error) }`, satisfaite par `*sql.DB` et `*sql.Conn`.
  - `ittest.Profile(t *testing.T, envName string) (sqlq.Profile, sqlq.SecretResolver)` (saute si
    absent, échoue si le profil n'est pas `readwrite` ou n'a pas `environment = "lab"`) ;
    `ittest.NewDatabase(t *testing.T, server *sql.DB, collation string) string` (crée
    `godta_it_<runID>` avec Query Store `READ_WRITE` et `QUERY_CAPTURE_MODE = ALL`, et l'enlève
    en `t.Cleanup` par `ALTER DATABASE … SET SINGLE_USER WITH ROLLBACK IMMEDIATE; DROP DATABASE`).
    En mode `AUTO`, trois exécutions d'une requête bon marché ne sont pas toutes captées, et
    certaines requêtes pas du tout (relecture du plan, mesuré sur 2022) ;
    `ittest.OpenDB(t, p sqlq.Profile, r sqlq.SecretResolver, db string) *sql.DB` (pool ouvert
    sur cette base par `conn.Open`, fermé en `t.Cleanup`) ;
    `ittest.RunWorkload(t, db *sql.DB, n int)` (exécute `n` fois chaque requête de l'annexe A
    bis, puis `sp_query_store_flush_db`). La charge passe par `sp_executesql` pour les requêtes
    paramétrées et par des lots simples pour les autres, jamais par une procédure temporaire :
    le Query Store de la base ne capte pas les instructions d'une procédure `#` (mesuré :
    aucune ligne, même en mode `ALL`) ;
    `ittest.LoadDataset(t, db *sql.DB)` (le jeu `godta_t` du spike : 1 000 000 lignes,
    `a` asymétrique, `b = a*10 + i%3`, `c = i%50000`, vue indexée `godta_v`, index filtré
    `godta_filt` sur `a = 933`, tas `godta_h` de 200 000 lignes avec `nix_h_x`, table
    `godta_cs` à columnstore non cluster ; texte exact dans `ittest.go`, repris de
    `build-small.sql` du spike, cité en annexe A).

### Tâche 6 : rejeu

Fichiers :
- Créer : `tools/internal/godta/replay/replay.go`, `replay_test.go`

Interfaces :
- Consomme : `model.Query`, `model.Workload`, `showplan.Statement`.
- Produit :
  - `type Kind string` : `"adhoc"`, `"proc"`, `"batch_locals"`, `"unreplayable"`.
  - `type Replay struct { Kind Kind; Setup []string; Call string; Teardown []string; SetOptions []string; Reason string }`
  - `replay.Build(q model.Query, st *showplan.Statement, w *model.Workload, tempProc string) Replay`.
  - `replay.SetStatements(opts int64) []string` : une instruction `SET x ON|OFF` par option, bits
    `ANSI_PADDING 1`, `CONCAT_NULL_YIELDS_NULL 8`, `ANSI_WARNINGS 16`, `ANSI_NULLS 32`,
    `QUOTED_IDENTIFIER 64`, `ARITHABORT 4096`, `NUMERIC_ROUNDABORT 8192` ; plus
    `SET DATEFIRST <n>` et `SET DATEFORMAT <f>` depuis `q.DateFirst` et `q.DateFormat` ;
    `date_format` est un `smallint` (mesuré : `1` pour `us_english`), traduit par une table
    `1 mdy`, `2 dmy`, `3 ymd`, `4 ydm`, `5 myd`, `6 dym`, à vérifier contre la doc de
    `sys.query_context_settings` avant d'écrire le test ; une valeur hors table rend la requête
    `unreplayable`, `"unknown date_format <n>"`.
  - `replay.Build` reçoit le plan de la requête (`*showplan.Statement`) en plus du texte, pour
    les règles qui lisent les objets.

  Règles, dans cet ordre (spec §8.5, mesurées au spike) :
  1. déclaration : le préfixe `(@…)` est détaché du corps, découpé au premier niveau de
     parenthèses (`decimal(10,2)` reste entier) ; une instruction de procédure (`ObjectID > 0`)
     n'a pas de préfixe : sa déclaration vient alors des `Param` du plan (`DataType` tel quel),
     appariés par nom ;
  2. genre d'instruction : on lit le premier mot-clé de chaque instruction du corps, après les
     commentaires `--` et `/* */`, les points-virgules (`;WITH`) et les parenthèses ouvrantes ;
     chaque instruction doit commencer par `SELECT`, `WITH`, `INSERT`, `UPDATE`, `DELETE`,
     `MERGE`, ou par `DECLARE` et `SET @` (affectation de variable locale) ; sinon
     `unreplayable`, `Reason = "statement kind: <MOT>"` (le Query Store garde des plans de
     `CREATE INDEX`, `CREATE STATISTICS`, `RESTORE` sous un type `SELECT`). La règle porte sur
     le corps, après la règle 1 : `(@s int)DECLARE @s int = (SELECT 1)` passe ;
  3. `SELECT … INTO` : `unreplayable`, `"select into"` (création d'objet) ;
  4. objets du plan : un `Access` sur une table temporaire (`#`), une variable table (`@`), une
     autre base que celle de la charge, ou un objet absent de `w.Tables` : `unreplayable`, avec la

### Tâche 10 : évaluation sur le serveur

Interfaces :

  - `type Session struct { /* *sql.DB de la base, *sql.Conn épinglée, dbID, enterprise, compileTimeout, lockTimeout */ }`,

    est abandonnée (délai dépassé, `ErrNotAPlan`), état de session rejoué.

    `type execer interface { Exec(ctx context.Context, sql string) error; Query(ctx context.Context, sql string) ([][]any, error) }` ;
    `NewSession` l'implémente sur le `*sql.Conn`, et `evaluate.NewRecordingSession(inst conn.Instance) (*Session, *Recorder)`
    (fichier `testing.go`, exporté pour les tests des tâches 10 et 18) donne une session qui
    enregistre les instructions et rend des plans écrits d'avance : c'est la « session
    factice » des tests unitaires.

  - `(*Session) Reset(ctx) error` ; `(*Session) DeclareReal(ctx, t *model.Table, hide map[int]bool) error`
    (type 0 avec `pages = 0` pour chaque index réel non cluster actif, hors ceux de `hide` ;

    `ErrAutopilotOff`), exécute `r.Call` sous `context.WithTimeout(compileTimeout)`, exige un
    seul jeu de résultat contenant un document `ShowPlanXML` (sinon `ErrNotAPlan` et la connexion
    est fermée, jamais réutilisée), remet `OFF`, exécute `r.Teardown`. Rend la dernière
    instruction du plan.
  - `evaluate.HypotheticalPages(rows int64, keyAndIncludeBytes, clusteredKeyBytes float64) int64`
    = `ceil(rows × (keyAndIncludeBytes + clusteredKeyBytes + 8 + 2) / 8096)`, au moins 1
    (mesuré : 3 308 contre 3 314 réelles).

  Déroulement de `Run`, par table (spec §8.5) :
  1. requêtes sur une table `HasColumnstore` : `not evaluated: columnstore`, sans rien envoyer

     `AutoCreatedStats` de la fin ;
  3. pour chaque requête retenue, écritures comprises : `Compile(showplan)` sans `AUTOPILOT` d'abord, puis `Reset`,

  `UsedHypothetical` de toutes les mesures combinées de ses requêtes, alors qu'un autre y figure,
  est au mieux `discuss`, avec la note `"made redundant by <ID>"`. Une mesure dont `Notes`
  contient `"unreliable estimate"` (tâche 19) interdit `recommended`.

## Annexe A : jeu de données des tests d'intégration

Repris du script `build-small.sql` du spike (spec §15), à recopier dans `ittest.go` :

```sql
ALTER DATABASE SCOPED CONFIGURATION SET MAXDOP = 2;
CREATE TABLE dbo.godta_t (id int IDENTITY CONSTRAINT pk_godta_t PRIMARY KEY, a int NOT NULL, b int NOT NULL, c varchar(20) NOT NULL, pad char(200) NOT NULL DEFAULT '');
WITH n AS (SELECT TOP (1000000) ROW_NUMBER() OVER (ORDER BY (SELECT NULL)) i FROM sys.all_columns x CROSS JOIN sys.all_columns y)
INSERT dbo.godta_t (a, b, c) SELECT a, a*10 + (i % 3), CONVERT(varchar(20), i % 50000) FROM n CROSS APPLY (SELECT CAST(POWER(ABS(CHECKSUM(NEWID())) % 1000 / 1000.0, 4) * 1000 AS int) a) z;
EXEC('CREATE VIEW dbo.godta_v WITH SCHEMABINDING AS SELECT a, COUNT_BIG(*) n FROM dbo.godta_t GROUP BY a');
CREATE UNIQUE CLUSTERED INDEX godta_v_cx ON dbo.godta_v(a);
CREATE INDEX godta_filt ON dbo.godta_t(c) WHERE a = 933;
CREATE TABLE dbo.godta_h (x int NOT NULL, y varchar(40) NOT NULL);
INSERT dbo.godta_h SELECT TOP (200000) ABS(CHECKSUM(NEWID())) % 10000, CONVERT(varchar(36), NEWID()) FROM sys.all_columns x CROSS JOIN sys.all_columns y;
CREATE INDEX nix_h_x ON dbo.godta_h(x);
CREATE TABLE dbo.godta_cs (k int PRIMARY KEY, v int);
INSERT dbo.godta_cs SELECT TOP 10000 ROW_NUMBER() OVER (ORDER BY (SELECT NULL)), 1 FROM sys.all_columns;
CREATE NONCLUSTERED COLUMNSTORE INDEX ncci_cs ON dbo.godta_cs(v);
```

Le script s'exécute avec `QUOTED_IDENTIFIER ON` (sinon la vue indexée échoue, erreur 1935,
mesuré) ; le chargement prend quatre secondes environ sur `sql2022` (mesuré par trois
relecteurs). Les valeurs sont aléatoires : les tests comparent la source et le labo ou l'avant
et l'après, jamais un nombre de lignes absolu. Une base neuve chargée ainsi n'a de statistique
de colonne que sur `a` (créée avec la vue ou l'index filtré) : `b` et `c` n'en ont pas, et la
statistique de `pk_godta_t`, bâtie sur la table vide, est périmée. Ce sont les cas que l'ordre
de l'étape 3 de `Run` (tâche 10) doit tenir.
