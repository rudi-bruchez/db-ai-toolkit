## Concluded by reading

**Hypothesis — silent parameter truncation (highest cost).** Task 5's `BindValue` checks `utf8.RuneCountInString(value) <= t.Length` for `nvarchar(n)`, `nchar(n)`, and `sysname` (plan line 1671). SQL Server defines `n` in UTF-16 byte pairs, so a supplementary character consumes two units while Go counts one rune. A passed value such as an emoji can pass validation for `nvarchar(1)` although the server cannot store that same value in the declared variable. This violates design §11's guarantee that the reported `-param` is the value the server used. Count UTF-16 units or refuse supplementary characters; add a case covering the boundary. Engine behavior is from [Microsoft's nchar/nvarchar documentation](https://learn.microsoft.com/en-us/sql/t-sql/data-types/nchar-and-nvarchar-transact-sql?view=sql-server-ver17), not a live instance observation.

**Hypothesis — overrides can rewrite the wrong span.** `AnalyseOverrides` returns parameters in marker `params=` order, but task 5's `Rewrite` applies them in reverse slice order (plan lines 1649–1660), assuming that is reverse SQL offset order. Design §8 does not require marker order to match declaration order. With `params=b,a` and `DECLARE @a ...; DECLARE @b ...;`, the earlier replacement shifts the later stored offset; the batch sent to SQL Server can be corrupted while `saved.params` still reports the supplied values. Sort replacements by descending `start`, and test a marker order opposite the declarations. The supplied twelve tests use one override at a time, so their passing result cannot catch this.
