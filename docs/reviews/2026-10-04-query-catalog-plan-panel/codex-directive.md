## Concluded by reading

**Hypothesis 5 — task 12 can present incomplete validation as complete.** Step 4 says to run every bundled query once, then run parameterized entries a second time with passed values. Three shipped queries (`object-references.sql`, `proc-source.sql`, `view-diagnose.sql`) require `@name` on the first run; §9 and `prepareSaved` refuse a missing parameter before connecting. The step supplies no exact command or value for those first runs and no exact first-lot marker list. Its later commit text claims every marked and bundled entry ran, which the written procedure cannot establish. This is also a direct instance of the plan's “show the step, not ‘similar to’” rule.

**Hypothesis 6 — task 2's setup violates the repository's only-access-through-`sqlq` rule.** Its shell block polls readiness with `podman exec ... sqlcmd ... -Q "SELECT 1"` (plan lines 538–545). AGENTS.md says all SQL Server access goes through `sqlq` and forbids ad-hoc `sqlcmd` calls. An implementation agent following this block would take the prohibited second connection path. I did not run it, as instructed.

**Hypothesis 7 — the plan leaves two §16 regression requirements without effective tests.** The design names `TestVerifiedHashesBytesThatRan` and `TestBoundQueryRefusedOnAnotherProfile`. No task defines either test. Task 7 checks hash changes between separate catalogue loads, and profile visibility in a list; neither exercises a file changing between load and successful run, nor the `-saved` code 1 path on a different profile. The implementation code captures `e.Hash` from the catalogue load, which appears sound by reading, but the stated tests would pass if these two requirements regressed.

**Hypothesis 8 — tasks 9 and 10 are not independently executable instructions.** Task 9 shows fragments but describes the three-way `readQuery` replacement and the surrounding `run`/`-allow-write` wiring in prose; task 10 says to call `checkSave` “just after” the guard and insert the post-execution block without showing the resulting `run`. A worker who sees only its own task must infer control flow, option fields, imports, emission count, and which branch owns `namedArgs`. The fragments use earlier names consistently (`CatalogConfig`, `Entry`, `SavedRun`, `Rewrite`, `RecordVerified`), and task 10's `O_EXCL` prevents overwrite, but the plan-specific rule explicitly requires showing these edits. The existing `-query`/`-file` messages, exit codes, and `-allow-write` behavior cannot be certified from the written patch.

**Hypothesis 9 — a successful `-save-query` may leave a file without its required verification record.** Task 10 checks the result of `writeSavedQuery`, then discards `RecordVerified`'s error with `_ =`. Section 10 says every successful `-save-query` writes or updates the registry. A registry I/O failure would leave a saved file and exit 0 while the next catalogue lists `verified:null`. The SQL did run and `O_EXCL` prevents overwriting an existing file; the defect is the unreported, missing attestation.

END` was accepted, consistent with [SQL Server variable scope](https://learn.microsoft.com/sql/t-sql/language-elements/variables-transact-sql).

Thus rows before a later SQL error, notices, showplan, and the final set have a plausible path through the code. This is a source-code conclusion, not a server run.
- Task 7's normal fixture order matched all 10 expected entries, including omission of unmarked SQL; its hash is computed once from the loaded tsql-scripts bytes after removing the marker line, as §10 specifies, and task 9 passes that captured hash to the registry after execution.
