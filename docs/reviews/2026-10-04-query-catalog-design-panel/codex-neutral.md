## Concluded by reading

**Hypothesis — a successful run can silently use a different parameter value from the one in `saved.params`.** The exact §9 rewrite assigns the caller's string to a declared variable, `DECLARE @database_name sysname = @sqlq_database_name;`, and §15 says conversion is left to SQL Server. For a marked `DECLARE @x nvarchar(5) = ...`, `-param x=Customer` would record `Customer` but the variable can hold only five characters. Microsoft documents that `ANSI_WARNINGS` is not honored when declaring and setting variables in a batch, and an overlong character value is truncated; `sysname` itself is `nvarchar(128)`. I could not execute SQL Server here, so this is an engine-behavior hypothesis grounded in [Microsoft's `SET ANSI_WARNINGS` documentation](https://learn.microsoft.com/en-us/sql/t-sql/statements/set-ansi-warnings-transact-sql) and its [`nvarchar`/`sysname` definition](https://learn.microsoft.com/en-us/sql/t-sql/data-types/nchar-and-nvarchar-transact-sql). Reject or check loss of value before presenting a bound string as the value used; the promised error path for invalid `bit`/`int` values does not cover this case.

**Hypothesis — the registry can present an unexecuted variant as verified.** §8 hashes the original on-disk file, not the rewritten SQL, and says one success verifies it “quelles que soient les valeurs passées.” Under §9, a run with `-param database_name=ERP` executes a changed declaration, while the file's default declaration never runs. The next catalogue listing nevertheless reports that original file as `verified`, and the same status applies to a later run with a different or omitted parameter. This contradicts §§4–5's narrower promise that the binary attests to what actually ran. Define verification at the executed variant and parameter set, or label the current field explicitly as “one variant executed” so an untested default is not presented as tested.

**Hypothesis — the specified dirty-read detector misses a supported SQL Server spelling.** §10 sets `dirty_reads` when sanitized text contains `READ UNCOMMITTED` or `NOLOCK`. The real clone uses `WITH (READUNCOMMITTED)` without a space, for example in `diagnostics/tempdb/version-store-content-by-index.sql:17` and `server-information/os-memory.sql:4`; `Sanitize` preserves that token. On the literal two-spelling rule, a marked script using only this hint would be listed as `dirty_reads:false`, allowing the skill to use its output for a correctness question. [Microsoft's table-hint documentation](https://learn.microsoft.com/en-us/sql/t-sql/queries/hints-transact-sql-table) says `READUNCOMMITTED` permits dirty reads. Include that token in the detection rule; no SQL Server run was available to test the resulting catalogue field.

**Hypothesis — profile-free listing cannot represent profile-dependent collisions with one `rejected` field.** §6 defines a collision in the names visible from profile P, but §10 makes `-list-queries` require no profile and gives each entry a single `rejected` state. If `bundled/x.sql` and `personal/P/x.sql` coexist, `x` must be rejected for P while the bundled `x` remains usable for Q. Listing both as rejected falsely hides Q's valid query; listing neither as rejected falsely offers P an ambiguous query. Specify profile-qualified listing or a per-profile collision state before implementing the JSON contract.

**Hypothesis — verification can attach to bytes that were never sent.** §8 says to hash the file “sur disque” after a successful `-saved` run, but does not require hashing the exact bytes read for execution. If that means reopening the path after the query, a file edited during a long run can receive a registry hash for new SQL that never ran. If it means retaining and hashing the bytes already read, this problem disappears. State the latter explicitly, and use the same executed snapshot when `-save-query -file` writes its personal copy; this is a race inferred from the sequencing, not a reproduced implementation bug.

**Hypothesis — existing bundled headers are invalid under the claimed unchanged format.** §7 says a `Parameter:` or `Parameters:` line declares parameters and that the already delivered format remains unchanged. Two delivered files instead say `No parameter.`: `blocked-processes-check.sql:3` and `missing-indexes.sql:4`. If that field is required, both become `rejected` on day one; if it is optional and parameters are inferred as empty, the parser rule needs to say so. The proposed `TestDeclaredParametersMatchTheSQL` does not resolve which reading is intended.

**Hypothesis — the main save command omits a newly mandatory flag.** §4 prints `sqlq -profile prod-erp -query "<sql>" -save-query orders-late`, while §§7 and 10 make `-summary <texte>` mandatory with `-save-query`. Literal use of the documented command would return a usage error rather than save the successful run. Amend the command or change the requirement; this is a design inconsistency, not a CLI behavior I could run without a server.
