## Verified by running

**1. The §9 override can silently change the value passed with `-param`.** I ran `rtk go run ./cmd/zzreview` from `tools/` with a temporary program calling the real `sqlq.Sanitize`, `FindWrites`, `FindBatchSeparators`, and `FindContextChanges`. For the literal batch `DECLARE @p int = 1; SET @p += 2; SELECT @p;`, it printed `guard=true` and `sanitized="DECLARE @p int = 1; SET @p += 2; SELECT @p;"`. Prepending contiguous header lines `-- Example` and `-- sqlq: name=example params=p` makes a §7 entry, and none of §9's five catalog refusals catches `SET @p += 2`: its assignment refusal is literally `SET @p =`. With `-param p=5`, the specified rewrite sends `DECLARE @p int = @sqlq_p; SET @p += 2; SELECT @p;`. [Microsoft documents that `+=` assigns the sum back to the variable](https://learn.microsoft.com/en-us/sql/t-sql/language-elements/set-local-variable-transact-sql?view=sql-server-ver17), so the expected answer is 7 while the result's `saved.params.p` says 5. The engine outcome follows documentation; it was not observed on a server here. Likewise, `SELECT @x = 3, @p = 2` after declaring `@x` evades the literal `SELECT @p =` refusal, and [Microsoft documents multi-variable SELECT assignment](https://learn.microsoft.com/en-us/sql/t-sql/language-elements/select-local-variable-transact-sql?view=sql-server-ver17). Every parameterized tsql-scripts answer remains suspect until all assignment targets to a marked variable are handled.

**2. `dirty_reads` misses a real, guard-passing hint.** The same Go corpus scan printed `files=344 pass=214 GO=98 writes=110 USE=38` and `readuncommitted_hint=8` among the passing files. One is `server-information/os-memory.sql`, whose executable line is `FROM sys.dm_os_sys_memory WITH (READUNCOMMITTED)`. §10 checks only `READ UNCOMMITTED` or `NOLOCK`, so the specified output would be `dirty_reads:false`. [Microsoft lists `READUNCOMMITTED` and `NOLOCK` as table hints](https://learn.microsoft.com/en-us/sql/t-sql/queries/hints-transact-sql-table?view=sql-server-ver17). This suppresses the warning AGENTS.md requires for correctness questions. A comment containing those words is not a false positive because `Sanitize` blanks comments.

**3. Passing the guard does not mean the script gives `sqlq` a usable answer.** The Go scan printed `passing=214`, `two_leading_selects=60`, `print=4`, `nocount=108`, `isolation=161`, `table_variable=0`, `insert_table_var=0`, and `no_top=208` (the last means no `TOP (` token, not that every file is unbounded). A definite example is `cloud/azure/azure-sql-database/service-level-info.sql`: it passes the guard and has separate top-level SELECTs at lines 11 and 16. `tools/cmd/sqlq/main.go:316-350` stores only the first non-showplan result set and silently drains the second. The current skill says `PRINT` and low-severity `RAISERROR` output is not captured. `SET NOCOUNT ON` is harmless because sqlq already sets it; script-set isolation runs after the preamble and may override it. `DECLARE @t TABLE` followed by `INSERT @t` is rejected by `FindWrites`, so those are outside the 214. A guard-passing script can also exceed the default 30-second timeout. Without SQL Server, the exact number of 214 files that produce a complete, usable answer is unknowable; 214 must not be presented as that count.

**4. The literal header rule can hide a marker or publish a license as the summary.** A read-only `rtk python3` scan implementing §7's contiguous leading `--` rule printed `sql_files 344 existing_markers 0 blank_splits_leading_dash_block 45 summary_anomalies 6`. In the guard-passing `diagnostics/IO/dm_io_virtual_file_stats.sql`, the description ends on line 5, line 6 is empty, and the license and closing dash lines are 7–8. Put `-- sqlq: name=io-virtual-file-stats` beside the license and §7 ignores it; put it before line 6 and it is found. The guard-passing `diagnostics/Memory/resource-semaphore.sql` and `diagnostics/query-store/longest-queries-in-a-period.sql` have blank descriptions, so §7 selects `rudi@babaluga.com, go ahead license` as their summary. The real `waits-statistics.sql` starts with a provenance URL and contains `GO`; its §10 example of an accepted, verified entry cannot describe that file as it stands. The tsql-scripts `CLAUDE.md` template is contiguous, but these real headers are not all instances of it.

## Concluded by reading

**5. Hypothesis — the §9 delimiter rule has two materially different readings.** For the exact batch `DECLARE @p varchar(10) = 'a;b'; SELECT @p;`, the real Go program printed `sanitized="DECLARE @p varchar(10) =      ; SELECT @p;"` and `guard=true`. §9 says to find positions in `Sanitize`, apply the rewrite to the original, then stop at the first `;` on the same line. Searching sanitized text finds the statement delimiter and works; searching original text finds the semicolon inside the literal and leaves broken SQL. State explicitly which text supplies the delimiter. The position guarantee itself held for the tested accented CRLF sample: the program printed `runes=37/37 bytes=38/37` for `-- é\r\nDECLARE @p int = 1;\r\nSELECT @p;`; rune offsets and line breaks survive, byte offsets do not.

**6. Hypothesis — `verified` can describe a batch that never ran.** §8 hashes the file on disk, but §9 sends rewritten text. One successful parameter value marks the original file verified for every value, including defaults never executed. If a file is edited between reading it for execution and hashing it for the registry, the new bytes may be recorded against the old batch. The design specifies no same-snapshot read/hash or before/after equality check. Hash the exact bytes read for the run and distinguish source verification from a particular rewritten invocation. The real `Sanitize` did not normalize CRLF in the checked sample, so CRLF alone is not the issue.

**7. Hypothesis — concurrent runs can erase each other's verification.** §8 specifies a temporary file and `rename`, which makes a replacement atomic but does not serialize two read-modify-write cycles. If processes A and B read the same old JSON and finish different `-saved` runs, the later rename drops the earlier entry, although both runs report success. A lock or equivalent serialized merge is needed to retain both facts.

**8. Hypothesis — profile-free listing has no defined collision view.** §6 defines visibility and name collisions from profile P, but §10 requires `-list-queries` without `-profile`. Listing only generic entries hides saved `personal/P` queries; listing every profile directory cannot assign one `rejected` value to a name that collides only for P, and reveals the profile taxonomy. A manually added `personal/_generic/tables-largest.sql`, or a tsql-scripts marker with that name, makes both entries rejected under §6 and disables the bundled query used by the skill. `-save-query` prevents an ordinary collision in its selected profile, but manual files and markers do not pass through that check. Define the profile-free view and what happens to a bundled query on collision.

**9. Hypothesis — the proposed catalogue still publishes an estate map.** AGENTS.md excludes server and database from `-list-profiles` because every session's output goes to the model provider. §10's `-list-queries` still prints human-written summaries, relative paths, rejection reasons, and `verified.profile`. A summary or path component can name a client, host, or database; a rejection copied from the current guard's `statement "..." uses ...` text can expose SQL identifiers; `verified.profile` reveals which profile ran which query and when. Relative paths prevent absolute path leakage but do not sanitize their components. These fields need an explicit disclosure rule before the skill calls the list at every session start.

**10. Hypothesis — `-save-query` can verify an invalid generated file.** §7 says the summary and `Parameters:` line are supplied through the single `-summary "<texte>"` flag, but §10 defines neither a separate parameter declaration nor escaping or validation of that text. One plausible implementation treats it as plain summary and derives `Parameters:` from SQL; another expects the agent to include header syntax in the flag. The resulting files differ. An embedded newline or `*/` can terminate the comment header even after the query succeeded, while §8 would then mark the saved file verified. Specify parameter derivation and validate or escape the summary before saving. The 2 September design expected every saved query to have a parseable header; §12 does not identify a change to that guarantee.

## Not a problem

- The real guard totals match §3's headline: 344 files, 214 passing, 98 with GO, and 38 with USE.
- `Sanitize` preserved rune count and line breaks in the checked accented CRLF sample; a rune-indexed rewrite can use those offsets.
- The existing bundled queries' `/* … */` headers use the documented `Parameter:` or `Parameters:` form; no existing `Heavy: yes` line changes their classification.
- `SET NOCOUNT ON` is already in sqlq's preamble; the first-result-set behavior is also documented by the current skill, although the new catalogue must account for it.
- No `sqlq:` markers exist in the read-only tsql-scripts clone, so nothing is accidentally catalogued yet.
- A clone move alone keeps the registry's relative key and content hash stable; two paths to the same marked file would instead collide by name under §6, making both entries visibly rejected.
- The temporary `tools/cmd/zzreview` programs were removed after the Go runs. No SQL Server instance or profile was accessed.
