## Verified

**Important — `INCLUDE` widening is prescribed for clustered primary keys.** [missing-index-reading.md:50](plugins/sqlserver-toolkit/skills/live-query/references/missing-index-reading.md:50) says a unique index or primary key “is widened through `INCLUDE` only,” without restricting that operation to nonclustered rowstore indexes. For a clustered primary key on `[a]` and a suggestion on `[a], [b]`, following the preceding subset rule and this exception produces a proposal to add `INCLUDE ([b])` to the clustered primary key. That operation is invalid, and the clustered leaf already contains the table’s columns. Microsoft defines `INCLUDE` as adding nonkey columns to a **nonclustered** index. Restrict the widening rule accordingly; preserving uniqueness does not make every index eligible for `INCLUDE`. Checked against [CREATE INDEX documentation](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql?view=sql-server-ver17#arguments).

**Important — the protocol applies ordered-prefix coverage rules to hash indexes.** [missing-index-reading.md:41](plugins/sqlserver-toolkit/skills/live-query/references/missing-index-reading.md:41) instructs comparison with each existing index’s leading keys; its memory-optimized exception only removes included columns. A hash index on `(a,b)` would therefore be judged to serve a suggestion with equality on `a`, or equality on `a` and inequality on `b`. Microsoft states that a hash seek requires equality predicates on **every** key column; inequality predicates revert to a scan. The resulting proposal could wrongly retain or widen a hash index instead of proposing a suitable memory-optimized nonclustered index. Check `index_type` before applying these rules. This is documentation-established behavior, not an engine observation: [Microsoft’s hash-index guidelines](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide#memory-optimized-hash-index-design-guidelines).

**Minor — the contract test accepts regressions that invalidate its named guarantees.** [missing_indexes_query_test.go:29](tools/internal/sqlq/missing_indexes_query_test.go:29) checks for token patterns anywhere in sanitized SQL, rather than their effective predicates or query position. In read-only, in-memory mutation checks, all positive patterns still matched after adding `OR 1 = 1` to the suggestion cap, adding it to the database filter, bypassing the user-object restriction, or adding `ps.partition_number` to the size aggregation’s grouping. These changes introduce no forbidden tokens. Respectively, they can cut table blocks at the final `TOP (70)`, misattribute another database’s suggestions through colliding object IDs, show excluded objects, or duplicate existing-index rows and report partition sizes separately. The Go suite itself was not executable here; these were pattern checks, not claimed Go test runs. The test needs focused checks for these structural invariants, or narrower claims about what it protects.

**Minor — uptime can pass the one-day gate before one day has elapsed.** [missing-indexes.sql:252](plugins/sqlserver-toolkit/skills/live-query/queries/missing-indexes.sql:252) uses `DATEDIFF(minute, start, GETDATE()) / 1440.0`. `DATEDIFF` counts minute boundaries rather than elapsed minutes. A start at `00:00:59` and evaluation the next day at `00:00:00` yields `instance_uptime_days = 1` after only 23:59:01, so the protocol permits conclusions before its prescribed threshold. Removing `ROUND` did not fully address the boundary issue. Checked against [DATEDIFF’s documented boundary semantics](https://learn.microsoft.com/en-us/sql/t-sql/functions/datediff-transact-sql?view=sql-server-ver17).

## Concluded by reading

**Important — set inclusion can falsely establish full equality-key coverage.** [missing-index-reading.md:45](plugins/sqlserver-toolkit/skills/live-query/references/missing-index-reading.md:45) says that when the equality set is a subset of the existing leading keys, “in any order,” the key already serves the equalities. Consider equality columns `{a,b}` and an existing key `(a,x,b)`, with no predicate on `x`: the stated subset condition holds, but the intervening unconstrained key prevents the proposed full equality-prefix seek. An agent following the rule can recommend only adding payload columns to `INCLUDE`, leaving the requested access path unresolved. Require the first **N consecutive** keys to equal the N-column equality set, with no intervening unrelated key. This consequence is inferred from the rule and Microsoft’s guidance that leading-key order controls index usefulness; it was not tested on an engine. See [Microsoft’s index design guidance](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide#column-considerations).
