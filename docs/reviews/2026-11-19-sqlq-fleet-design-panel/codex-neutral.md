# Relecture de la spec sqlq sur un parc

## Verified by running

La section 4.2 promet un contexte de connexion par tentative, mais ce contexte ne borne pas le prélogin quand `connectTimeoutSec` est absent. J'ai exécuté `cd tools && go run ./cmd/zzreview` avec le vrai pilote `go-mssqldb` v1.11.0, `database/sql`, et un serveur TCP local qui accepte puis reste muet deux secondes avant de fermer. Le programme utilisait la DSN `sqlserver://u:p@127.0.0.1:<port>?encrypt=disable` et `context.WithTimeout(..., 500*time.Millisecond)` pour `db.Conn(ctx)`. Sortie : `mode=hang_ctx accepts=1 elapsed=2.001s error=*net.OpError ... read: connection reset by peer ... isDeadline=false`. Avec `connection timeout=1`, le même serveur donne `mode=hang accepts=1 elapsed=1.001s error=*net.OpError ... i/o timeout ... isDeadline=false`. Le profil autorise `ConnectTimeoutSec == 0` et sa DSN omet alors `connection timeout` (`tools/internal/sqlq/dsn.go`). Le contexte seul ne réalise donc pas le délai annoncé pour chaque tentative ; un tunnel qui garde le socket ouvert peut bloquer le parc au-delà de tous les délais prévus. Il faut fixer un délai de connexion effectif même quand le profil n'en fournit pas, et vérifier sur un serveur muet que l'appel se termine à ce délai. Le programme temporaire a été supprimé.

## Concluded by reading

Hypothèse de défaut : la section 5.4 écarte de `rows` les lignes d'un profil dont les colonnes diffèrent, mais le compte dans `profiles_ok` et laisse `profiles_failed` à zéro. La section 5.6 demande à l'agent de lire `profiles_failed` avant les lignes, sans lui demander de chercher `columns_differ` ou de lire `profiles[].rows`. Deux instances qui réussissent avec des éditions différentes d'une vue peuvent donc produire `profiles_ok: 2`, `profiles_failed: 0`, code 0, et un tableau agrégé ne contenant qu'une instance. C'est une réponse incomplète qui ressemble à une réponse complète. Les deux lectures possibles de « réussi » sont succès de la requête ou présence de ses lignes dans l'agrégat ; la spec choisit la première pour le compteur et la seconde pour `rows`, sans signal global de cette différence. Le test d'intégration annoncé vérifie `columns_differ`, mais pas que le consommateur détecte les lignes omises.

Hypothèse de défaut : l'accord de production est donné pour les noms montrés par `-list-profiles` avec une sélection, puis `-profiles-match` ou `-all` recalcule la sélection lors d'un second processus (sections 5.1 et 5.6). Le fichier de profils peut être régénéré entre les deux commandes. Un nouveau profil `prod` correspondant au motif entre alors dans l'exécution sans avoir figuré dans la liste approuvée, alors que la spec dit expressément que le oui ne couvre pas une sélection élargie. Il manque un moyen de lier l'appel à la liste approuvée, ou de refuser quand elle change. Le comportement opposé, considérer le oui comme portant sur le motif futur, contredit la dernière phrase de 5.6 et la règle de `AGENTS.md` imposant un oui avant la première requête sur chaque profil `prod`.

Hypothèse de défaut : la règle d'injection de la colonne `profile` en 5.4 est définie « un jeu de résultats » à la fois, alors que `columns` décrit le premier profil réussi. Si le premier jeu n'a pas de colonne `profile` et qu'un autre en a une, deux lectures sont possibles : choisir `profile` pour le schéma global et `sqlq_profile` pour le second, auquel cas `rows` et `columns` n'ont pas la même clé ; ou choisir `sqlq_profile` pour tout le parc, ce qui requiert de connaître tous les schémas avant de construire les lignes. La règle actuelle ne tranche pas. Dans les deux cas, elle doit dire comment les colonnes différentes sont reconnues et comment les lignes sont rangées sans écraser la valeur renvoyée par SQL Server.

Hypothèse de défaut : la section 5.6 ne dit pas comment appliquer aux entrées `-saved` de parc les règles existantes du skill `live-query` : lire le header avant la première exécution, annoncer une entrée `verified: null`, et obtenir un oui distinct pour `heavy: true` sur `prod`. Une lecture considère que l'accord sur la sélection `prod` suffit, l'autre conserve le second accord pour une requête lourde ; seule la seconde respecte le contrat actuel. Comme le catalogue est chargé une fois sans profil (5.3), la spec doit préciser le contrôle de ces métadonnées avant tout lancement et le texte que l'agent montre à l'utilisateur.

## Not a problem

- Avec le faux serveur qui ferme dès l'acceptation, `db.Conn` a fait une seule ouverture et a rendu `EOF` ou `ECONNRESET` ; les deux sont observables pour `connect_transient`.
- Avec `connection timeout=1`, le pilote a rendu un `*net.OpError` de délai et non `context.DeadlineExceeded` ; `errors.As` vers `net.Error` permet de classer ce cas sans dépendre du texte.
- `database/sql` ne fait pas de réessai caché dans les quatre cas mesurés : `accepts=1` à chaque appel, cohérent avec `connect_attempts: 1` avant un réessai explicite.
- `path.Match` donne bien à `*` la portée d'un seul segment de chemin, ce qui correspond à la sélection `'prd/*'` décrite.
- `cd tools && go test ./cmd/sqlq ./internal/sqlq` a terminé avec `248 passed in 2 packages` avant la rédaction du rapport.
