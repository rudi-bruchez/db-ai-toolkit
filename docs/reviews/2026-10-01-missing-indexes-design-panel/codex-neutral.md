## Verified

Revue documentaire et statique uniquement : aucune connexion, aucune exécution SQL, aucun fichier modifié. Les constats concernant le moteur reposent sur les passages Microsoft cités, pas sur une observation expérimentale. Sept défauts établis ci-dessous, classés du résultat silencieusement trompeur vers l’échec visible.

**1. La définition des colonnes existantes ne suffit pas à établir la couverture (§4, §6).** Microsoft précise : « Columns implicitly added because they're part of the clustering key aren't listed in `sys.index_columns`. » Les listes prévues peuvent donc faire croire qu’une colonne manque à un index alors qu’elle est déjà disponible implicitement. Par exemple, avec une clé clustered `Id` et un index nonclustered sur `Status`, l’absence de `Id` dans `included_columns` ne démontre pas qu’il faut l’ajouter. L’invariant sur les colonnes de partitionnement assume également leur omission, sans expliquer au protocole de lecture comment traiter cette couverture. Conserver des listes de colonnes déclarées est possible, mais leur sémantique doit être explicite et la lecture doit reconstituer la couverture implicite avant de proposer un élargissement. [Documentation `sys.index_columns`](https://learn.microsoft.com/en-us/sql/relational-databases/system-catalog-views/sys-index-columns-transact-sql?view=sql-server-ver17).

**2. `filter_definition = NULL` ne signifie pas nécessairement « non filtré » (§4).** La documentation donne trois causes : « NULL for heap, nonfiltered index, or insufficient permissions on the table. » Le contrat ne conserve pas `has_filter`, alors que le design prévoit précisément des utilisateurs dont la visibilité est limitée. Une table visible peut donc présenter un index filtré dont le prédicat reste invisible ; `suggestions_on_hidden_objects` ne détecte pas ce cas puisque l’objet lui-même est visible. La comparaison pourrait traiter cet index comme couvrant toutes les lignes. Ajouter `has_filter` et imposer « couverture inconnue » lorsque `has_filter = 1` et que la définition est NULL. [Documentation `sys.indexes`](https://learn.microsoft.com/en-us/sql/relational-databases/system-catalog-views/sys-indexes-transact-sql?view=sql-server-ver17).

**3. `observed_days` surestime potentiellement la fenêtre des compteurs existants (§5, §6).** Microsoft indique : « whenever a database is detached or is shut down […] all rows associated with the database are removed ». Une instance démarrée depuis trente jours peut donc avoir des compteurs de cette base depuis quelques minutes. Le design connaît cet effacement, mais le protocole exige seulement de citer `observed_days` et la limite de fenêtre *par table*, laquelle concerne les suggestions. Citer trente jours à côté de compteurs nuls peut ainsi donner une ancienneté trompeuse à une proposition de suppression. Définir `observed_days` comme une borne supérieure depuis le démarrage de l’instance, et exiger une fenêtre d’usage effectivement établie avant toute recommandation fondée sur zéro. [Documentation `sys.dm_db_index_usage_stats`](https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-objects/sys-dm-db-index-usage-stats-transact-sql?view=sql-server-ver17).

**4. Le traitement de la troncature n’assure pas la comparaison complète promise (§6, §7).** Dans `tools/internal/sqlq/result.go`, `Add` exécute `rs.RowCount++`, puis, lorsque la limite est atteinte, `rs.Truncated = true; return` : `sqlq` conserve simplement un préfixe du résultat. Avec `context`, puis toutes les suggestions avant les index existants, 149 suggestions de la première table peuvent remplir les 150 lignes sans montrer aucun de ses index. Les autres tables peuvent disparaître entièrement ; il ne s’agit donc pas seulement d’une « dernière table […] incomplète ». Le protocole demande uniquement de signaler la troncature, puis permet une proposition consolidée. Il faut interdire cette proposition pour toute table dont l’inventaire n’est pas établi complet, et définir comment récupérer les détails manquants. Le `rowcount` global ne permet pas, à lui seul, d’identifier une frontière complète entre tables.

**5. Le protocole général d’élargissement est incorrect pour les tables en mémoire (§4, §6).** La documentation des suggestions dit : « All columns of the table are included in every memory-optimized index. » Elle demande donc d’ignorer `included_columns` pour ces index. Le design affiche ces colonnes telles quelles et distingue les tables en mémoire seulement pour les compteurs, puis applique à toutes les tables le même protocole d’élargissement. Une suggestion d’inclusion pourrait produire une recommandation inutile ou inapplicable. La référence de lecture doit comporter une branche explicite pour les tables en mémoire ; le marqueur `usage_not_tracked` ne suffit pas puisqu’il désigne aussi les index spatiaux. [Documentation `sys.dm_db_missing_index_details`](https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-objects/sys-dm-db-missing-index-details-transact-sql?view=sql-server-ver17).

**6. Le `TOP (5)` borne les tables, pas le résultat, contrairement à la règle du dépôt (§4, §7).** `AGENTS.md` impose : « Always bound the result with `TOP (n)` in the query. `-maxrows` is a backstop, not a substitute ». Le design exige toutes les suggestions et tous les index des cinq tables, sans borne du SELECT final. Le code confirme que `scanAll` continue avec `for rows.Next()` après que `RowSet` a cessé de conserver les lignes : `-maxrows 150` ne limite donc pas le travail ni les lignes transférées. Il faut résoudre explicitement le contrat entre exhaustivité et borne de présentation. Un `TOP (150)` ajouté seul déplacerait le problème : il pourrait cacher la coupure côté serveur sans déclencher `truncated`.

**7. Les droits annoncés ne couvrent pas la mesure de taille, et M9 est incompatible avec les prérequis documentés (§5, §8).** Pour `sys.dm_db_partition_stats`, Microsoft exige avant 2022 « `VIEW DATABASE STATE` and `VIEW DEFINITION` permissions », puis à partir de 2022 « VIEW DATABASE PERFORMANCE STATE and VIEW SECURITY DEFINITION permissions on the database ». Le droit serveur annoncé ne constitue donc pas le contrat complet. Surtout, sur la version 2019 prévue pour la validation, M9 retire précisément `VIEW DEFINITION` tout en attendant un résultat contenant le compteur d’objets cachés. La lecture de cette DMV ne peut pas être supposée fonctionner dans ces conditions. Ajouter les droits de base et décider si l’absence de droits de taille provoque une erreur ou une branche qui conserve le diagnostic avec `used_mb = NULL` ; adapter M9 à cette décision. [Documentation `sys.dm_db_partition_stats`](https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-objects/sys-dm-db-partition-stats-transact-sql?view=sql-server-ver17).

## Concluded by reasoning

**8. Hypothèse de recommandation dangereuse : « élargir plutôt que créer » pourrait modifier une garantie d’unicité (§6).** Aucun comportement futur de l’agent n’est confirmé, mais la règle ne distingue pas l’ajout d’une colonne incluse de l’extension d’une clé unique. Microsoft établit : « A unique index guarantees that the index key contains no duplicate values. » Remplacer `UNIQUE(A)` par `UNIQUE(A, B)` permettrait désormais deux lignes ayant le même `A` et des `B` différents. C’est potentiellement le défaut le plus coûteux si le skill conduit à cette proposition. Les indicateurs `is_unique` et `is_primary_key` sont disponibles, mais aucune instruction ne demande d’en préserver la sémantique. Ajouter cette obligation, distinguer clé et INCLUDE, et identifier les contraintes uniques avant de recommander une modification. [Guide de conception des index](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide).

## Not a problem

- **Score individuel** : la formule prévue est exactement celle de l’exemple Microsoft : `avg_total_user_cost * avg_user_impact * (user_seeks + user_scans)`. [Exemple documenté](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/tune-nonclustered-missing-index-suggestions?view=sql-server-ver17).
- **Groupe de suggestions** : Microsoft précise « An index group contains only one index » ; aucune multiplication interne au groupe n’est à inventer. [Documentation des groupes](https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-objects/sys-dm-db-missing-index-groups-transact-sql?view=sql-server-ver17).
- **Effacement des suggestions par maintenance** : « Performing an ALTER INDEX operation […] also clears missing index requests for that table » justifie l’avertissement prévu. [Documentation de conservation](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/tune-nonclustered-missing-index-suggestions?view=sql-server-ver17).
- **Compatibilité du garde** : `guard.go` ne refuse ni CTE, ni `UNION ALL`, ni `FOR XML`, ni `OPTION` ; une construction sans matérialisation reste envisageable.
- **Absence de `DECLARE`** : c’est une contrainte propre au design, pas une interdiction de `sqlq` ; le modèle `blocked-processes-check.sql` en utilise.
- **Un seul jeu de résultats** : il respecte `collect`, qui précise « Extra result sets beyond the first are drained, not reported ».
- **Dates converties en texte** : elles évitent la branche `time.Time` de `normalise`, qui utilise `value.Format(time.RFC3339Nano)` ; ce code seul ne prouve toutefois pas un suffixe `Z` universel.
- **Test automatique du garde** : `filepath.Glob(..., "*.sql")` prendra bien le futur fichier ; ce test ne valide ni la compilation SQL ni les calculs.
- **Taille incluant les LOB** : additionner `used_page_count` par partitions correspond à la définition documentée, qui inclut les pages LOB et de débordement. [Documentation des partitions](https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-objects/sys-dm-db-partition-stats-transact-sql?view=sql-server-ver17).
