## Verified

The design needs revision before implementation. The findings below are ordered by the cost of discovering them in use. SQL Server behavior is established from documentation, not from an engine test; no database connection or repository modification was made.

**1. `observed_days` cannot justify an index’s observation window (§§4–6).** The calculation is correctly described as “jours depuis le démarrage,” but the reading protocol then uses it to assess zero usage counters and possible deletion. Microsoft documents that database detach or shutdown removes that database’s usage rows: “all rows associated with the database are removed.” Consequently, an instance running for 90 days can contain a database attached or brought online this morning, with freshly empty counters. Restore likewise does not establish a 90-day observation history. Reporting `observed_days = 90.0` alongside zeros creates a plausible justification for removing a periodically used index. Rename this field to `instance_uptime_days` and explicitly prohibit treating it as the counters’ age; database transitions and index creation can shorten that window independently. [Index usage documentation](https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-objects/sys-dm-db-index-usage-stats-transact-sql?view=sql-server-ver17).

**2. The index lists omit effective coverage that the reading protocol needs (§§4, 6).** Microsoft states: “Columns implicitly added because they're part of the clustering key aren't listed in `sys.index_columns`.” Consider a table clustered on `Id`, with a nonunique nonclustered index on `A` including `B`: that nonclustered index also carries `Id`, but the prescribed lists report only `A` and `B`. A suggestion requiring `Id` as a covering column can therefore appear to require widening an index that already covers it. The explicit omission of implicit partitioning columns creates the same interpretation problem for partitioned indexes. This does not remove the index’s **row**, but it undermines the promise that those rows support a reliable comparison with suggestions. Label the lists as declared columns and require consideration of implicit clustering and partitioning coverage before recommending changes. [Index-column documentation](https://learn.microsoft.com/en-us/sql/relational-databases/system-catalog-views/sys-index-columns-transact-sql?view=sql-server-ver17).

**3. “Same leading columns, therefore widen” is an insufficient recommendation rule (§6).** Microsoft explicitly says the suggestion “doesn't specify an order for those columns.” Equality columns `[A], [B]` must therefore be compared as an equality set: an existing `(B, A)` prefix can serve those equalities despite differing from the DMV’s textual order. Conversely, sharing a prefix does not establish that widening is appropriate: the index can be filtered, disabled, unique, a primary key, or a different index type. Adding a key column to a unique `(A)` index changes the uniqueness guarantee to the combination, which is a semantic change. The protocol must preserve those properties and assess the inequality portion and implicit coverage. Its promise to choose equality order by selectivity also requires additional evidence: §4 contains neither selectivity nor workload predicates, and cannot determine whether a filtered index covers the relevant queries. Microsoft recommends reviewing definitions and workload tradeoffs; the displayed lists alone cannot support the consolidated recommendation promised here. [Microsoft’s tuning guidance](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/tune-nonclustered-missing-index-suggestions?view=sql-server-ver17).

**4. Five tables do not bound the final result, and `-maxrows 150` cannot guarantee their completeness (§§2, 4, 7).** `AGENTS.md` requires “Always bound the result with `TOP (n)` in the query”; `TOP (5)` on table selection leaves the expanded suggestions and indexes unbounded at the presentation level. In [result.go](tools/internal/sqlq/result.go:75), `RowSet.Add` executes `rs.RowCount++`, then sets `rs.Truncated = true` and discards rows beyond the cap. For one selected table with 100 suggestions and 60 indexes, the context consumes one slot, so only 49 indexes reach the caller. Later ranked tables may be entirely absent. Furthermore, §7’s “la dernière table est incomplète” is not always true: truncation can fall exactly between complete table blocks. The flag makes truncation detectable, but the protocol must suspend comparisons for any potentially incomplete table and provide a completion strategy. Resolve the final SQL bound and completeness contract explicitly; the existing blocked-process query does so with a final `TOP`, a total count, and an incompleteness indicator.

**5. The advertised permissions omit a required DMV and make M9 contradictory (§§3, 5, 8).** `used_mb` requires `sys.dm_db_partition_stats`, whose documented pre-2022 requirement is “`VIEW DATABASE STATE` and `VIEW DEFINITION`”; SQL Server 2022+ requires database-level `VIEW DATABASE PERFORMANCE STATE` and `VIEW SECURITY DEFINITION`. The server-state permissions listed in the specification are insufficient by themselves. On SQL Server 2019, M9’s login lacking `VIEW DEFINITION` therefore cannot be promised a normal result containing a positive hidden-object count when this DMV is read. The hidden-object counter itself is computable from server-visible missing-index details and an anti-join to visible `sys.objects`; lacking `VIEW DEFINITION` alone does **not** hide objects on which the login has another permission. Microsoft says subcomponent visibility follows permissions on the parent. Also, `sys.indexes.filter_definition` can be NULL for insufficient permissions, so NULL cannot universally mean “unfiltered”; include `has_filter` if restricted visibility remains supported. Document all permissions, decide whether unavailable size information causes failure or NULL, and revise M9 accordingly. The anti-join must distinguish genuinely invisible objects from deliberately excluded system objects. [Partition statistics](https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-views/sys-dm-db-partition-stats-transact-sql?view=sql-server-ver17), [metadata visibility](https://learn.microsoft.com/en-us/sql/relational-databases/security/metadata-visibility-configuration?view=sql-server-ver17), [index metadata](https://learn.microsoft.com/en-us/sql/relational-databases/system-catalog-views/sys-indexes-transact-sql?view=sql-server-ver17).

## Concluded by reasoning

**6. Hypothesis — reverse group cardinality leaves deduplication and total ordering unproved.** Microsoft establishes “An index group contains only one index,” but also says neither individual column is a key; their combination is the key. That establishes the group’s contents, not a documented guarantee that an `index_handle` occurs in only one group. If the same handle participates in multiple groups, emitting each joined row can repeat the suggestion, and ordering by score followed only by `index_handle` can leave ties. I cannot assert that such a state occurs on a supported engine. Nevertheless, the design’s unconditional deterministic-order promise needs either an established reverse-cardinality guarantee or an explicit grain and a final `index_group_handle` tie-breaker. Table-score ties are already resolved by `object_id`, and existing-index ties by `index_id` within each table. Separately, summing overlapping suggestion scores is a heuristic, not a proven additive estimate of benefit: one execution plan can contain several requests. Call the table total a ranking metric rather than savings. [Groups documentation](https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-objects/sys-dm-db-missing-index-groups-transact-sql?view=sql-server-ver17), [tuning guidance](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/tune-nonclustered-missing-index-suggestions?view=sql-server-ver17).

**7. Hypothesis — size aggregation could remove or multiply indexes unless its join contract is specified.** The design mandates an external usage join but does not prescribe the equivalent preservation rule for partition statistics. Joining raw partition rows can duplicate an index and its usage counters; an inner join to aggregated storage rows can remove an index without a matching row. The memory-optimized case particularly needs clarification: memory allocation is exposed through XTP-specific statistics, so partition page counts must not be presented as its memory footprint. I have not established an engine state proving that the proposed query would omit a memory-optimized index, because no query exists and the precise join is unspecified. Require a size relation aggregated by `(object_id, index_id)`, joined externally from `sys.indexes`, with explicit unavailable-size semantics. Partitioned tables should produce one index row with summed pages, never one row per partition. [Partition statistics](https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-views/sys-dm-db-partition-stats-transact-sql?view=sql-server-ver17), [XTP memory statistics](https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-objects/sys-dm-db-xtp-table-memory-stats-transact-sql?view=sql-server-ver17).

## Not a problem

- **Cross-database identity:** filtering both DMVs by `database_id = DB_ID()` and joining usage by both `object_id` and `index_id` prevents the described cross-database collision.
- **Ordinary index inventory:** starting from `sys.indexes`, excluding hypothetical indexes, and externally joining usage retains heaps, clustered, disabled, filtered and unused indexes; Microsoft describes one row per index or heap. [Documentation](https://learn.microsoft.com/en-us/sql/relational-databases/system-catalog-views/sys-indexes-transact-sql?view=sql-server-ver17).
- **Current cap detection:** the documented limits apply to groups, details and group statistics; 600 retained groups correctly flags present saturation, and additional uncollected requests do not make the count exceed 600. A later count below 600 cannot establish that saturation never occurred. [Groups](https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-objects/sys-dm-db-missing-index-groups-transact-sql?view=sql-server-ver17), [details](https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-objects/sys-dm-db-missing-index-details-transact-sql?view=sql-server-ver17), [statistics](https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-views/sys-dm-db-missing-index-group-stats-transact-sql).
- **Datetime rendering:** the claim is true for this dependency and DSN: the driver defaults to UTC, assigns that location during DATETIME decoding, and `normalise` returns `value.Format(time.RFC3339Nano)`; local server wall-clock values consequently acquire a misleading `Z`. [Rendering code](tools/cmd/sqlq/main.go:375).
- **Other JSON types:** the inspected driver returns FLOAT as `float64`, BIT as `bool`, DECIMAL as textual bytes and NVARCHAR as text; `normalise` preserves floats/booleans and turns decimal bytes into JSON strings, preserving their value rather than silently rounding it.
- **Display rounding:** `sqlq` does not round FLOAT scores itself; any required rounding must be explicit in SQL or in the answer.
- **Write guard:** `Sanitize` “blanks out comments, string literals and quoted identifiers”; tokenization preserves underscores, so header references to DDL, `'TableIsMemoryOptimized'`, XML expressions and `user_updates` are allowed. [Guard code](tools/internal/sqlq/guard.go).
- **SQL Server 2012:** no prescribed construct establishes a compilation failure; an unknown OBJECTPROPERTY property returns NULL, while `filter_definition`, the selected older DMV columns, XML aggregation and style 126 are compatible. Handle the property with `CASE WHEN ... = 1`, so its 2012 NULL becomes false. [OBJECTPROPERTY](https://learn.microsoft.com/en-us/sql/t-sql/functions/objectproperty-transact-sql?view=sql-server-ver17), [conversion styles](https://learn.microsoft.com/en-us/sql/t-sql/functions/cast-and-convert-transact-sql?view=sql-server-ver17).
- **Date text:** `varchar(19)` with style 126 deliberately drops fractional seconds and adds no timezone; that matches the proposed display contract.
- **Static guard test:** the glob automatically includes the future SQL file, but proves only guard acceptance—not compilation, permissions, completeness or the 600-entry engine behavior. [Test code](tools/internal/sqlq/bundled_queries_test.go).
- **Scope:** multi-database iteration and SQL overlap scoring are explicitly deferred; the actual Todoist task text is not quoted in §§1/9, so a further dropped requirement cannot be verified from this specification.
